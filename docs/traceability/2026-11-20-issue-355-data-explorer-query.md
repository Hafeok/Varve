Session prompt: Web UI, part 2 — the data explorer (#96)

What this is
Part 1 (#167, ADRs 0200 to 0206) shipped the operator console: `Varve.WebUi`, a Blazor WebAssembly host at layer 6. It reads the public API through `Varve.Protocol.Client` and has no endpoints of its own. Since #296 it ships in the container image and is served at `/ui/`.
Part 2 is the data explorer, #96's second deliverable:
Data explorer: SPARQL with as-of and diff, graphs, validation reports, entailment provenance
It is in 1.0 (#15). #96 closes with this part.
What is already decided
Do not re-open these. They are part 1's accepted ADRs and the maintainer's rulings:

* ADR 0200: `Varve.WebUi` is a host, never a library. No `src/` package references Blazor.
* ADR 0203: every screen reads through `Varve.Protocol.Client`. If a screen needs something the client doesn't expose, the client gains it as public API, in the baseline diff.
   * A screen that would need a new server route is out of scope and becomes an issue.
   * Data no route serves is never shown.
* ADR 0201 and ADR 0245: sign-in, the two tokens, `NotConfigured`, and settings generated by the server.
* ADR 0202: the Content Security Policy. No inline script, nothing from a third-party origin, nothing relaxed.
* ADR 0205: the size budget, and no AOT. Raising the budget is a dated amendment with the measured numbers.
* ADR 0206: `docs/ui/` is the design source.
   * The levels are a dependency rule, enforced by VARVE0006: `Atoms < Molecules < Organisms < Templates < Parts < Pages < App`.
   * A screen is composed of existing components and has a case under `docs/ui/screens/` before it is built.
   * New markup gets its contract case first, in the same commit as the component.
* Position and time are first class (part 1, point 6). Every view shows the `Varve-Position` it was read at, and an as-of view says so in its header. A view never mixes positions silently.
* Accessibility: WCAG 2.2 AA, audited in CI on every screen, with a recorded keyboard walk-through.

Rulings for this part

1. The explorer reads. It does not write.
   * SPARQL Query only. SPARQL Update, Graph Store writes and loading a file are out of scope; open one issue for them and link it from #96.
   * Reason: a write from a browser needs its own decisions (confirmation, the idempotency key source of #311, what an audit trail shows), and none of it is needed to explore.
2. The server decides what a reader sees. Results arrive already filtered by grants and row rules (ADR 0107, ADR 0238).
   * The explorer never says a thing does not exist. An empty result reads as "no rows returned to you", and a refusal is the problem as the server sent it (ADR 0242).
   * Nothing is cached across sign-ins or identities.
3. A query is bounded and can be stopped.
   * Results render incrementally from the streamed response, up to a stated row limit, with a visible "stopped at N rows" and a way to fetch on.
   * A running query has a cancel that aborts the request.
   * The server's own limits (ADR 0114) are shown as their problems, not hidden.
4. The query editor is ours, at level 2. `QueryEditor` is an organism: a real `textarea` over an `aria-hidden` coloured layer, with the browser doing all the editing.
   * What it shows: syntax colouring, a wavy underline at the parse error's line and column, line numbers, two-space tab and bracket matching.
   * One lexer and parser. Colouring and errors come from Varve's own lexer and SPARQL parser, running in the browser, so the editor and the server can't disagree.
   * Prerequisite: a public tokenizer in `Varve.Sparql` (layer 2), by its own ADR and with the public API baseline diff.
   * Alignment is CSS only: both layers sit in one grid cell, with no inline styles.
   * Growth: the `textarea` grows to its content, through `field-sizing: content` where supported and a few lines in `webui.js` elsewhere.
   * Timing: colouring is debounced to the next animation frame, so typing never waits on WebAssembly.
   * Not in this part: completion and auto-indent (level 3). File them as an issue that first decides which vocabulary queries completion may run, and under whose grants.
   * No editor engine of our own, and no JavaScript editor library.
5. The explorer's assemblies are lazy-loaded. The console's first screen keeps ADR 0205's budget. The explorer gets its own stated budget by dated amendment, with both numbers measured.
6. No client-side evaluation over a downloaded graph. Every answer comes from the server, under its grants, regime and position. Note it on #96 as out of scope.
7. Nothing is stored on the server for the explorer. Query history or saved queries, if you propose them, live in the browser only, per origin, and hold no result and no token. Say what is stored and for how long.
8. Entailment, as far as `main` serves it. Inference part 1 (#170) shipped tier 1 only: the rewriting regimes `rdfs`, `rdf` and `d`, the `Varve-Entailment` header, and the TBox binding. The views, the reserved graphs and `explain` are #171's, still in flight.
   * Marking inferred statements. A statement view (a resource, the graph neighbourhood) reads once under `simple` and once under the regime, both with the same `Varve-As-Of`.
      * What the regime added is marked inferred: a dashed edge, a dashed predicate underline, and the word "inferred". Never paleness alone.
      * SELECT rows are never marked. The results table says which regime answered.
   * "Why is this here" is a "Why?" control on an inferred `Triple` that calls `explain` and shows its proof tree. The rule is never shown without that call.
      * Until #171 serves `explain`, the control is a marked gap in the case and an issue, not a mock.
      * When #171 lands, closure regimes compare `varve:explicit` against the full read.
   * Change the `Triple` case's inline rule ("inferred · rdfs9") to "inferred" now.

The screens
Propose the final list in the plan, as a table: screen, the resource it reads, and the components it composes. The starting list:

   * the position it was read at and the request id;

* The graph view: a bounded neighbourhood around one resource, expanded on demand, under a node budget, with the resource view's table one control away (`docs/ui/README.md`, "The graph view").

   * Layout: deterministic and radial, computed in C#. The resource sits in the centre, its neighbours on a ring ordered by predicate, and an expanded neighbour's own neighbours on an arc outside it. No physics simulation. The same data always gives the same picture, so a diff between positions keeps unchanged nodes in place.

* Provenance: for a statement, whether it is explicit or inferred, and for an inferred one what entails it, as far as `main` serves it (ruling 8).
