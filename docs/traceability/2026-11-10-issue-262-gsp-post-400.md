## The report

**The cause: neither side.** The runner didn't send a short body and the
server didn't parse a short read. The 400s happen on every run, they are
correct, and the baseline already exempts them. Neither job the issue cites
failed because of them. The evidence, posted on the issue:

- **Both sightings' failures are the exempt cases.** #234's publish dry run
  failed 40 of 11097 cases, and its ratchet read `Exempt: 40. … Regressed:
  0.`; the job failed later, at SBOMs. `land/pr-238`'s container job failed 6,
  and its ratchet read `Exempt: 6. … Regressed: 0.`; the job failed later,
  when the step fetching the Actions OIDC token got an empty response.
- **The column is the end of the body, and it depends on the subject.** The
  deprecated transcript's line 3 has no final `.`. After the runner's rewrite
  it is 54 chars in process and 70 against the image, so the parser reports
  `line 3, column 55` in the #234 log and `column 71` in the 2026-11-10 log.
  It isn't intermittent: the column differs by subject, and stays the same
  from run to run.
- **The server side was already guarded.** `SlowSenderTests` (#127, #129)
  sends Graph Store bodies in segments, with `Expect: 100-continue` and
  chunked, plain and multipart.

**What was changed** (`tests/Varve.Conformance.Tests` only):

1. **A failing request states what it sent.** `SentContent` counts the bytes
   it writes, and a status the transcript doesn't expect is reported with
   `(sent Content-Length N, wrote N bytes: <body>)`. In this session's run
   `post__existing_graph@memory` reads `Content-Length 100, wrote 100 bytes`,
   and the body ends at `"Jane Doe"`.
2. **The runner's rewrite compares texts, not lengths.** It used to compare
   the rewritten text's char count with the body's byte count, and take
   equality for "unchanged". The guard test
   `A_rewritten_body_is_sent_rewritten_whatever_its_length_in_chars` sends a
   body with one two-byte char whose rewrite adds one char. It failed with
   the length comparison put back (checked in this session) and passes with
   the fix. These suites' bodies are ASCII, so this wasn't the cause seen
   here. It was the one place on the runner side that could send the wrong
   body.
3. **An exempt failure says so.** The message starts `exempt
   (baseline/exemptions.txt), expected to fail:`. For the image (`@server`)
   the memory store's exemptions are read, as CI's ratchet reads them. The
   outcome stays failed, so the ratchet's counts don't change.

**Tests run:** `ProtocolGuardTests` and `ProtocolConformanceTests` in
process, 144 cases. 132 pass, and the 12 that fail are the 12 exempt cases,
each marked as such.

**The gate's 20 runs** were counted from the run history, not re-run. The
ratchet fails a job on any regression, so a passed Ratchet step is a run in
which this sequence did what the baseline expects. The 20 most recent
`container` jobs had a passed Ratchet step. They are 10 CI runs × two
architectures, from 2026-11-10 09:11 UTC to the `land/pr-238` runs. So did the
20 most recent `publish` jobs, from 2026-11-03 to 2026-11-10. No Ratchet step
in that window failed. The job ids are on the issue.

**Left for the maintainer:** the OIDC-token step in the container job, and
the SBOMs step in Dependabot's publish dry run, are the two failures the
sightings actually were. Neither is in this change; the session offered on
the issue to file them.

**After the pull request opened.** Its own `container (linux-x64)` job failed
the same way as `land/pr-238`: the ratchet passed (`Exempt: 6 … Regressed:
0`), then the step that fetches the Actions OIDC token handed python an empty
body. `curl --silent --fail` hides the error from the token service, and the
same step passed on `land/pr-238`'s second attempt. So the fetch is now
retried four times, says why it failed (`--show-error`), and stops at curl
under `pipefail`. Checked locally against an unreachable address: curl's
retries and its error print, and the step exits non-zero.
