# Varve.Benchmarks

Not in CI, and not a gate. ADR 0027: a benchmark that gates turns a noisy
measurement into a flaky build, and a shared runner is the noisiest machine
there is. Numbers are taken deliberately, on a stated machine, and reported
with the machine.

```bash
dotnet run -c Release --project tests/Varve.Benchmarks -- --filter '*'
```

## Milestone 3a — reading 100,000 N-Quads

**Machine.** Intel Xeon @ 2.80 GHz, 4 logical and 4 physical cores, 15 GiB RAM,
Ubuntu 24.04.4 LTS (kernel 6.18.44), a cloud container rather than dedicated
hardware. .NET SDK 10.0.401, runtime 10.0.12, X64 RyuJIT `x86-64-v4`.
BenchmarkDotNet 0.15.8, `--warmupCount 3 --iterationCount 8 --invocationCount 1
--unrollFactor 1`. Baseline: dotNetRDF (`dotNetRdf.Core` 3.5.2).

**Dataset.** Generated by `Dataset.cs`, so the run reproduces without a file:
100,000 quads across five named graphs, seventeen predicates, one subject in
eight a blank node, and objects mixed between IRIs, plain literals, typed
literals, language-tagged literals and literals carrying escapes. Deliberately
not a nice document — a parser that is fast only on IRIs is fast on the easy
half of the problem. It is still synthetic, and a real dataset has a different
term-length distribution, escape density and IRI-prefix profile.

| | Mean | Quads/s | Allocated | vs. dotNetRDF |
|---|---:|---:|---:|---:|
| Varve — views | 148.5 ms ± 1.8 | 673,000 | **856 B** | 19.0× faster |
| Varve — owned terms | 167.0 ms ± 5.1 | 599,000 | 24.5 MB | 16.9× faster |
| Varve — into `InMemoryDataset` | 401.4 ms ± 5.5 | 249,000 | 90.2 MB | 7.0× faster, 7.3× less memory |
| dotNetRDF — `TripleStore` | 2,826.5 ms ± 53.6 | 35,000 | 660.7 MB | — |

**Read the third row, not the first, for the comparison.** The first row is not
doing dotNetRDF's work: it hands out views over the parser's own buffer and
owns nothing, which is the point of the streaming path and is not a graph
anybody can query afterwards. The third row builds a queryable dataset with
interned terms, which is the like-for-like run, and it is **7.0× faster and
uses 7.3× less memory**. The 19× headline is real but it is measuring a
different thing, and quoting it without this paragraph would be dishonest.

**856 bytes for 100,000 quads** is one `TermArena` — the same figure
`AllocationTests` reports as the fixed cost of a parse, arrived at
independently. The allocation test asserts zero *per quad*; this is what that
looks like at a hundred thousand.

**What is not measured.** Writing, the pull reader, the streaming entry points,
`ReadOnlySequence` fragmentation, and anything at all about query. Parsing is
the only thing milestone 3a ships, so it is the only thing benchmarked.

## Milestone 3b — reading 100,000 quads of Turtle

**Machine.** Intel Xeon @ 2.10 GHz, 4 logical and 4 physical cores, Ubuntu
24.04.4 LTS (Noble Numbat), a cloud container rather than dedicated hardware.
.NET SDK 10.0.401, runtime 10.0.12, X64 RyuJIT `x86-64-v4`. BenchmarkDotNet
0.15.8, default job. Baseline: dotNetRDF (`dotNetRdf.Core` 3.5.2).

**A different machine from the 3a section above** — 2.10 GHz here, 2.80 GHz
there — so the two sets of absolute numbers are not comparable with each other.
The ratios within each table are.

**Dataset.** Generated by `TurtleDataset.cs`. Every statement carries a
prefixed name to expand, a predicate-object list, an object list, a blank node
property list and a two-item collection, so the measurement is of what Turtle
adds over N-Quads rather than of line splitting.

```
$ dotnet run -c Release --project tests/Varve.Benchmarks -- --datasets
N-Quads: 15,644,119 bytes, 100,000 quads, 156.4 bytes/quad
Turtle:  1,106,705 bytes, 100,000 quads,  11.1 bytes/quad
```

**Do not read quads per second across the two sections.** Both documents carry
100,000 quads and the Turtle one is **fourteen times smaller**, because a
collection's four `rdf:first`/`rdf:rest` quads cost almost no bytes to write
down. Per quad Turtle therefore looks far faster than N-Quads; per byte it is
slower, which is the honest direction — it is doing more grammar. The quad
count is checked at `[GlobalSetup]` rather than asserted here, so a parser that
quietly stopped halfway could not produce a flattering number.

| | Mean | Quads/s | Allocated | vs. dotNetRDF |
|---|---:|---:|---:|---:|
| Varve — views | 16.7 ms ± 0.6 | 6,000,000 | **6.1 KB** | 44.4× faster |
| Varve — owned terms | 28.8 ms ± 0.6 | 3,470,000 | 37.2 MB | 25.8× faster |
| Varve — into `InMemoryDataset` | 100.2 ms ± 2.0 | 998,000 | 54.8 MB | **7.4× faster, 5.5× less memory** |
| Varve — read and write back | 38.4 ms ± 0.8 | 2,600,000 | 15.0 MB | — |
| dotNetRDF — `Graph` | 742.0 ms ± 14.5 | 135,000 | 301.2 MB | — |

**Read the third row, not the first**, for the same reason as milestone 3a: the
streaming rows hand out views over the parser's own buffer and own nothing,
which is not a graph anybody can query afterwards. The like-for-like run builds
a queryable dataset with interned terms, and it is **7.4× faster and uses 5.5×
less memory**. The 44× headline is real and it is measuring a different thing.

The **fourth row has no baseline on purpose**: it reads the document and writes
Turtle back out, and dotNetRDF's writer was not measured, so there is nothing
honest to divide by. It is here because a round trip is what the fixed-point
property test exercises 569 times, and this says what it costs.

**6.1 KB for 100,000 quads** is the parse's fixed cost — the arena and the
prefix table — and it does not grow with the document. `AllocationTests`
asserts zero bytes *per quad* on the same reader; this is what that looks like
at a hundred thousand.

**What is not measured.** The pull reader, the streaming entry points,
`ReadOnlySequence` fragmentation, error recovery, and query. A document whose
statements are one triple each would move every row, because the per-statement
costs — the arena reset, the pending buffer — would then be paid per quad.

## Milestone 4 — the in-memory store

**Machine.** Intel Xeon @ 2.10 GHz, 4 logical and 4 physical cores, 15 GiB RAM,
260 MiB L3, Ubuntu 24.04.4 LTS, a cloud container rather than dedicated
hardware. .NET SDK 10.0.401, runtime 10.0.12, X64 RyuJIT `x86-64-v4`.
BenchmarkDotNet 0.15.8. No baseline: dotNetRDF's in-memory store has no log,
no effective deltas and no as-of reads, so a comparison would time different
work. Oxigraph remains owed (ADR 0027).

```bash
dotnet run -c Release --project tests/Varve.Benchmarks -- --store-sizes
dotnet run -c Release --project tests/Varve.Benchmarks -- --filter '*CommitBenchmarks*' \
  --warmupCount 2 --iterationCount 8 --invocationCount 1 --unrollFactor 1
dotnet run -c Release --project tests/Varve.Benchmarks -- --filter '*ScanBenchmarks*' \
  --warmupCount 3 --iterationCount 10
```

**Dataset.** Generated by `StoreDataset` in `StoreBenchmarks.cs`: 1,000,000
quads, 100,000 subjects of ten quads, seventeen predicates, a sixth of the quads
in the default graph and the rest across five named graphs; objects are shared
IRIs, canonical integers (inline ids, no dictionary entry), plain and
language-tagged literals, and non-canonical integers (dictionary entries).
769,188 distinct terms take a dictionary entry. Loaded as 100 commits of 10,000.

### Size

| | Bytes | Per quad |
|---|---:|---:|
| The six key arrays of the default projection (ADR 0041) | 192,000,000 | **192.0** |
| A checkpoint: the six arrays, the dictionary, a header | 228,971,219 | 229.0 |
| The log: 100 commits, records, headers and chain | 68,989,323 | 69.0 |
| Managed heap growth for the whole store (log, dictionary, runs, one checkpoint) | 579,084,176 | 579.1 |

### Commits

| | Mean | Throughput | Allocated |
|---|---:|---:|---:|
| 100,000 quads in one commit, into an empty dataset | 175.2 ms ± 8.9 | 571,000 quads/s | 160.9 MB |
| 100,000 quads as 100 commits of 1,000 | 260.0 ms ± 7.9 | 385,000 quads/s | 272.9 MB |
| 1,000 single-quad commits of new terms, into 100,000 quads | 6.6 ms ± 0.7 | 150,000 commits/s | 6.4 KB per commit |

A commit includes normalisation against the head, the dictionary, SHA-256 of
the body and the header, the append, and the default projection's update —
everything T1 does. The memory backend's durability is `None`, so no flush
costs anything; a file backend's `fsync` will dominate small commits.

### Scans, over a pinned read of 1,000,000 quads

| | Mean | Quads | Throughput | Allocated |
|---|---:|---:|---:|---:|
| Every quad, every graph | 22.1 ms ± 1.2 | 1,000,000 | 45 M quads/s | 320 B |
| One predicate of seventeen (a POSG range) | 1.39 ms ± 0.11 | 58,824 | 42 M quads/s | 320 B |
| The default graph (a graph-first range) | 4.47 ms ± 0.26 | 166,667 | 37 M quads/s | 320 B |
| 10,000 subject lookups (SPOG ranges) | 7.8 ms ± 0.6 | 100,000 | 0.78 µs per lookup | 320 B per lookup |

320 bytes is one cursor and its stream array, per scan, whatever the scan
returns: the scan itself allocates nothing per quad, which `AllocationTests`
asserts and this shows at a million.

### Against ADR 0012's revisit condition

ADR 0012 is to be superseded if "milestone 4 benchmarks of index size and scan
throughput contradict the choice" of 64-bit counter-allocated ids. **They do
not.** Index size is 192 bytes per quad for six orders; the content-derived
128-bit ids the ADR rejected would make the same layout 384. Scan throughput is
37–45 M quads/s single-threaded, allocation-free, over merged runs. Neither
number argues for a wider id. What the benchmark cannot yet test is the ADR's
locality and compression hypothesis on disk, which is milestone 6's layout.

## Milestone 5a — parsing the SPARQL syntax corpus

**Machine.** Intel Xeon @ 2.80 GHz, 4 logical and 4 physical cores, 15 GiB,
Ubuntu 24.04.4 LTS (Noble Numbat), kernel 6.18, a cloud container rather than
dedicated hardware. .NET SDK 10.0.401, runtime 10.0.12, X64 RyuJIT
`x86-64-v4`. BenchmarkDotNet 0.15.8, default job. Baseline: dotNetRDF
(`dotNetRdf.Core` 3.5.2, `SparqlQueryParser` and `SparqlUpdateParser`).

The same clock as the milestone 3a section and a different one from 3b and
4; as before, absolute numbers are comparable only within a section and the
ratios are comparable everywhere.

**Corpus.** Loaded by `SparqlCorpus` in `SparqlBenchmarks.cs` from the W3C
submodule, and printed rather than asserted in prose:

```
$ dotnet run -c Release --project tests/Varve.Benchmarks -- --sparql-corpus
1.0 and 1.1 corpus: 215 queries both parsers accept (0 that dotNetRDF rejects left out), 15,415 bytes
1.2 corpus: 120 cases, 13,386 bytes
large update: 12,910 bytes
```

The first corpus is every positive *query* case of the SPARQL 1.0 and 1.1
syntax suites, parsed at version 1.1 by both parsers, with a case left out if
dotNetRDF refuses it so that the two rows time the same work. None were left
out. The second is every positive case of the six SPARQL 1.2 syntax suites,
queries and updates together; dotNetRDF has no SPARQL 1.2, so that row has no
baseline. The third is `syntax-update-2/large-request-01.ru`, an `INSERT DATA`
of 868 quads, the one input in the suites that is big enough to measure by
itself. Each row parses its whole corpus once, so a mean is the cost of the
corpus and not of a query; the per-query figures below are that mean divided
by the count.

| | Mean | Per case | Bytes/s | Allocated | vs. dotNetRDF |
|---|---:|---:|---:|---:|---:|
| Varve — 1.0 and 1.1 corpus, 215 queries | 761 µs ± 26 | 3.5 µs | 20.3 MB/s | 304 KB | **8.0× faster, 13.4× less memory** |
| dotNetRDF — 1.0 and 1.1 corpus, 215 queries | 6,065 µs ± 115 | 28.2 µs | 2.5 MB/s | 4,066 KB | — |
| Varve — the same, parse and write back | 866 µs ± 28 | 4.0 µs | — | 304 KB | — |
| Varve — 1.2 corpus, 120 cases | 578 µs ± 15 | 4.8 µs | 23.2 MB/s | 324 KB | no baseline |
| Varve — large update, 868 quads | 985 µs ± 29 | 1.1 µs per quad | 13.1 MB/s | 474 KB | **4.5× faster, 5.1× less memory** |
| dotNetRDF — large update, 868 quads | 4,441 µs ± 69 | 5.1 µs per quad | 2.9 MB/s | 2,442 KB | — |

**The corpus is small, and that is the caveat to read first.** Fifteen
kilobytes of queries is the whole positive syntax corpus, and it fits in the
L2 cache; a workload of long queries with long literals would move every row,
and there is no such corpus in the suites. What the table measures is the
parser's dispatch across every construct of the grammar on realistic query
sizes, which is the shape a query engine sees, and not bulk throughput, which
is what the Turtle sections measure.

**The allocation is the tree.** 304 KB over 215 queries is 1.4 KB per query,
and it is all algebra: immutable records with their lists and the interned
terms, which is what the parse returns. `AllocationTests` asserts that parsing
350 more triple patterns allocates exactly what building them by hand does,
so the parser's own working set — its token buffer, pooled lists and the
interning table — is rented and returned and shows here as nothing. The
milestone 3b reader's 6.1 KB fixed cost is the same idea; the difference is
that a parse's result here is a tree the caller owns.

**The third row has no baseline on purpose**, as at milestone 3b: it parses,
serialises the algebra back to text and discards the text, and dotNetRDF's
formatter was not measured. It says that writing costs about a seventh of
parsing, with no allocation beyond the tree, because the output buffer is
rented once at set-up. It is the property the round-trip test exercises 3,000
times per run.

**The large update is slower per byte than the small queries**, 13 MB/s
against 20, and that is the direction to expect: the queries are mostly
keywords and short names, while the update is 868 terms each resolved against
`BASE`, validated as an IRI and interned, then held in a `QuadPattern` record
apiece. 474 KB for 868 quads is 560 bytes per quad, which is the record, its
four terms and the `RdfTerm` behind each, and the ratio against dotNetRDF is
narrower here because its cost per term is also mostly the term.

**What is not measured.** Error paths, UTF-16 input (transcoded once at the
entry, at `Utf8.FromUtf16` speed), the rewriter, and anything after parsing;
nothing evaluates a query yet. The 1.2 row will get a baseline when another
.NET parser reads SPARQL 1.2. ADR 0050's evaluator benchmark, the one with a
revisit condition attached, is milestone 5b's and needs the evaluator first.
